# Spectrum Stable migration — integration contract

The project is Spectrum Stable. The existing Beta implementation cannot work with its UUID project ID and project secret.

## Parent-owned configuration changes (confirmed)

- Use only `SPECTRUM_PROJECT_ID` (UUID), `SPECTRUM_PROJECT_SECRET`, and `SPECTRUM_WEBHOOK_SECRET` (the Stable webhook's literal signing secret). Never read or silently reuse old `PHOTON_*` Beta values.
- Backend configuration/capability checks require the project ID and project secret. No `pho_prj_` / `pho_sk_` assumptions and no Beta bearer token fallback.
- `checkPhoton(projectSecret, projectId)` and `createPhotonWebhook(projectSecret, projectId, siteUrl)` keep their positional calling convention. These use Basic auth at `https://spectrum.photon.codes`, not `api.photon.codes/v1`.
- Stable webhook creation is `POST /projects/{projectId}/webhooks/` with `{webhookUrl: siteUrl + '/webhooks/photon', schemaVersion: 'normalized-events.v1', eventTypes: ['message.received']}`; secret is `data.signingSecret` in `{succeed:true,data}`. No `apiVersion`, `enabledEvents`, or destination endpoint. The current OpenAPI also returns `standardSigningSecret`; LifeLink deliberately uses the documented legacy `signingSecret` and `X-Spectrum-*` signature pair, which remains emitted. Do not supply the `whsec_` standard secret as `SPECTRUM_WEBHOOK_SECRET`.
- Existing dashboard users are reused with read-only `GET /projects/{projectId}/users/?type=shared`. No creating, replacing, deleting or emailing the four registered users during this migration.
- Stable webhook auth is `X-Spectrum-Timestamp`, `X-Spectrum-Signature: v0=<lowercase hex HMAC-SHA256>`, signing `v0:${timestamp}:${rawBody}` with the literal secret, ±5 minute tolerance. Payload is `{event:'messages',space,message}`. There are no Beta message delivery events or HTTP send endpoints.

## Runtime decision and essential dependency versions

Use an app-owned `"use node"` action with the official low-level `@photon-ai/advanced-imessage/grpc` transport. The Convex component's published sender **does not forward its clientGuid to Spectrum**; its own README warns of duplicate sends after lost acknowledgements. Installing that component would weaken LifeLink's existing consent/outcome semantics. Keep LifeLink's durable attempt/event tables and use the official low-level SDK's `clientMessageId` directly.

- `@photon-ai/advanced-imessage`: `2.3.0`, published 2026-10-14T11:16:06.618Z (10 days old).
- `@grpc/grpc-js`: `1.14.6`, published 2026-10-08T15:19:10.310Z (16 days old).

- `nice-grpc-common`: `2.0.4`, published 2026-08-04T18:14:00.611Z (81 days old).

These exact dependencies are installed in `packages/backend/package.json` and `bun.lock` using Bun 1.4.4 with `--minimum-release-age 604800 --ignore-scripts`. `packages/backend/convex.json` selects Node 24 and declares the four external packages. `integrations/photonruntime.ts` statically imports the gRPC peers; the local Node bundle retains all four external references. No Spectrum component mount is required. The generated app API type map includes the new Node action module. No runtime token is stored in function args or documents; the Node action reads the project secret and obtains a short-lived shared token using Basic auth. The endpoint and shared gRPC address are verified against Stable OpenAPI and the published `@spectrum-ts/imessage@12.11.0` cloud provider implementation. Every transport client is closed after use.

## Implemented contracts and handoff

- Existing public `imessage.register({contactId,confirmedHandle})`, `imessage.refresh({contactId})`, and `imessage.list({})` signatures remain unchanged. Registration only looks up an existing active shared user by exact `phoneNumber`; optional `email` metadata is not used as an allowlist identity. Missing registrations produce an actionable error without mutation. No automatic invitations or new shared-line users.
- Private `integrations.photonruntime.conversation({assignment})` mints a shared transport token, then reads bounded native chat history. It never sends or creates a chat. A verified inbound message binds `peerUserId` to the exact contact handle, `senderId` to `shared`, and `spaceId` to the provider's DM GUID.
- Private `integrations.photonruntime.send({body,idempotencyKey,photoStorageIds,route,reconciliation?})` checks the captured chat's single participant, loads every approved photo before sending, then sends photos and text with durable `clientMessageId` values. Reconciliation supplies its private `{actionId,attemptId,token}` claim identity. Partial success is unknown rather than safe-to-retry. No credentials cross Convex action arguments.
- `schema.ts` adds optional `imessageEnrollments.protocol: 'spectrum'`, `actions.reconciliation: {attemptId,token,expiresAt,phase: 'claimed' | 'dispatching'}`, and `executionAttempts.photonReconciliationUncertain: boolean`. Old Beta enrollment documents remain stored but cannot authorize Stable sends. The owner's next Set up iMessage action verifies and reuses the existing dashboard user. Existing execution-attempt route fields remain compatible; reconciliation requires the current Spectrum enrollment and the exact captured route.
- Verified webhooks are committed before HTTP acknowledgement, deduped by project + opaque message ID, and bound only to an explicitly enrolled owner/contact outside Practice mode. Unsupported Beta delivery events are ignored; no fake delivery/read receipt is inferred from an inbound webhook or send acceptance.
- Text-only reconciliation reuses the original `clientMessageId`. An explicit duplicate or a valid receipt proves acceptance; a current rejection cannot prove the earlier timed-out request did not happen. Photo-containing unknown attempts remain unknown rather than replaying only text and claiming full success.
- `checkPhoton` now verifies a successful Stable envelope rather than treating an arbitrary HTTP 200 as valid credentials. Existing webhook URL conflicts preserve the registration and explain that its original `signingSecret` is needed.

## Independent-review fixes completed

P1: `execution.claimReconciliation` replaces the unclaimed context query with an atomic two-minute claim. A concurrent check cannot enter. Manual settlement, cancellation and retry reject an active claim. Immediately before a reconciliation write, the Node sender calls `execution.authorizePhotonReconciliation`, which atomically consumes the `claimed` phase and verifies the exact attempt, token, deadline, body, original idempotency key, version fingerprint, valid approval, current owner/contact/enrollment, and captured route. Settlement and release require the same action/attempt/token; stale commits return `cannot_tell` rather than a definitive result. Settlement updates the attempt, action, receipt, message and journey in one mutation.

Timeouts do not prove an SDK request stopped. Expiry clears an unarmed claim safely; expiry after dispatch first persists `photonReconciliationUncertain`, preventing any further resend of that attempt. A rejected `runAction` promise cannot release a dispatching claim early. Ordinary completion releases its owned claim, including when the provider cannot tell. Expiry only restores the unknown outcome for investigation and positive manual confirmation; it never creates a safe failure. In particular, `markOutcome(false)` now refuses **all live Photon unknown attempts**, including original sends recovered by maintenance: absence of a message cannot prove that an outstanding request will never arrive. This keeps those attempts non-retryable and non-cancellable. Other providers retain their existing manual outcome behavior.

This deliberately does not use Convex's published ten-minute Node runtime limit as proof of termination. [Convex execution limits](https://docs.convex.dev/production/state/limits#execution-time-and-scheduling) and the [official Node executor](https://github.com/get-convex/convex-backend/blob/main/npm-packages/node-executor/src/executor.ts) do not provide provider-side cancellation or fencing for an outstanding SDK write. An abandoned dispatched check therefore requires confirmation of actual success; there is no invented negative receipt or automatic retry.

P2: the installed SDK's explicit refusal codes `contentDuplicateExceeded`, `burstRateExceeded`, and `newContactThrottled` now yield a safe failure before any photo/message was accepted. The existing partial-acceptance override keeps later failures unknown, and a new refusal during reconciliation never establishes failure of the original request. See [official error handling](https://photon.codes/docs/advanced-kits/imessage/error-handling).
